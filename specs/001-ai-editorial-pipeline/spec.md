# Feature Specification: AI Editorial Pipeline (全自动AI编辑部)

**Feature Branch**: `001-ai-editorial-pipeline`
**Created**: 2026-02-14
**Status**: Draft
**Input**: User description: "构建全自动AI编辑部，4个AI各司其职，7步全链路自动化处理新闻"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - RSS新闻自动采集与内容抓取 (Priority: P1)

系统每小时自动从63个RSS源拉取最新文章。对每篇新文章，同时启动三路内容抓取（Firecrawl、iFramely、Gemini兜底爬虫），按字段级别择优合并：标题取iFramely结果，正文取Gemini结果，图片取RSS原始数据。任何一路抓取失败不影响整体，其余两路自动兜底。

**Why this priority**: 内容采集是整个编辑部的数据入口，没有稳定的内容源，后续所有AI处理步骤都无法运行。这是MVP的基石。

**Independent Test**: 配置5个RSS源，触发一次采集周期，验证文章被正确拉取、三路抓取并行执行、字段级Winner选择逻辑正确输出合并后的文章数据。

**Acceptance Scenarios**:

1. **Given** 系统配置了63个RSS源, **When** 每小时定时触发拉取, **Then** 系统获取所有源的最新文章并去重存储
2. **Given** 一篇新文章被发现, **When** 三路抓取并行执行, **Then** 系统在每个字段上独立选择最优结果并合并为一条完整记录
3. **Given** Firecrawl服务不可用, **When** 系统抓取文章, **Then** iFramely和Gemini正常兜底，文章仍然被成功处理
4. **Given** 一篇文章在多个RSS源中重复出现, **When** 系统拉取, **Then** 文章被识别为重复并只保留一条记录

---

### User Story 2 - AI摘要生成与元数据标注 (Priority: P2)

每篇成功采集的文章自动送入AI摘要引擎（AI1），一次性生成：人类版TLDR（简洁摘要）、向量版TLDR（关键词密集的富信息版）、5个Key Points、重写标题、分类标签。生成结果与原始文章关联存储。

**Why this priority**: 摘要和元数据是后续向量化聚类和编辑评分的输入基础，且直接面向最终用户展示，是核心价值交付。

**Independent Test**: 输入10篇已采集的文章，验证AI为每篇生成完整的摘要包（2个TLDR+5个Key Points+重写标题+分类标签），且输出格式符合预定义schema。

**Acceptance Scenarios**:

1. **Given** 一篇完整采集的文章, **When** 送入摘要引擎, **Then** 系统生成人类版TLDR（≤100字）、向量版TLDR（≤300字，关键词密集）、5个Key Points、重写标题和至少1个分类标签
2. **Given** 文章正文为空或过短（<50字）, **When** 送入摘要引擎, **Then** 系统标记该文章为"内容不足"并跳过摘要生成，记录原因
3. **Given** 摘要引擎调用失败, **When** 重试3次仍失败, **Then** 文章标记为"摘要待生成"并进入重试队列，不阻塞其他文章处理

---

### User Story 3 - 向量化聚类与聚类扩展 (Priority: P3)

每篇文章的向量版TLDR被转换为高维语义向量（AI2）。系统使用近似最近邻搜索自动将语义相似的文章聚为一组（同一事件报道归类）。当某个聚类包含3篇及以上文章时，系统主动调用搜索API寻找更多相关报道并纳入该聚类，使信息覆盖更全面。

**Why this priority**: 聚类是将零散文章组织为事件视角的关键步骤，直接提升用户获取信息的效率。依赖US2的向量版TLDR输出。

**Independent Test**: 准备20篇涵盖5个不同事件的文章（每个事件4篇），验证向量化后聚类结果至少将同事件文章归为同组，且≥3篇的聚类触发扩展搜索。

**Acceptance Scenarios**:

1. **Given** 多篇已生成向量版TLDR的文章, **When** 执行向量化和聚类, **Then** 语义相似的文章被归入同一聚类，聚类内文章相似度高于跨聚类相似度
2. **Given** 一个聚类内文章数量达到3篇, **When** 聚类扩展触发, **Then** 系统调用搜索API查找相关报道并将符合条件的新文章纳入该聚类
3. **Given** 一篇文章与任何现有聚类的相似度均未达到阈值, **When** 系统处理, **Then** 该文章作为独立条目存在，不强制归入任何聚类

---

### User Story 4 - Gravity Engine编辑评分与排序 (Priority: P4)

每篇文章经过Gravity Engine（AI3）进行16维度深度评分。评分分为4个层面：影响力（行业影响/消费者影响/行动性/紧急度）、智识引力（新颖性/技术深度/二阶效应/开发者价值/谈资价值）、叠加信号（信噪比/传播潜力/早期趋势）、质量标记（公关水文/猜测/具体性/付费赞助）。输出编辑投票（Editorial Vote）和新颖性门槛（Novelty Gate: pass/fail）。未通过Novelty Gate的新闻不展示。

**Why this priority**: 评分排序是最终用户体验的核心——决定用户看到什么、不看到什么。依赖前序步骤的文章数据。

**Independent Test**: 输入30篇文章，验证每篇获得16维度评分、Editorial Vote和Novelty Gate判定。确认Novelty Gate为fail的文章不出现在最终排序结果中。

**Acceptance Scenarios**:

1. **Given** 一篇完整处理的文章, **When** 送入Gravity Engine, **Then** 系统输出4层面16维度的数值评分、Editorial Vote和Novelty Gate判定
2. **Given** 一篇Novelty Gate判定为fail的文章, **When** 生成最终展示列表, **Then** 该文章不出现在用户可见的内容流中
3. **Given** 评分引擎调用失败, **When** 重试后仍失败, **Then** 文章标记为"评分待完成"并进入重试队列，不影响已评分文章的展示
4. **Given** 传播潜力（Viral Potential）维度得分, **When** 生成展示视图, **Then** 该得分映射为文章气泡大小的视觉指标

---

### User Story 5 - 全链路编排与容错运行 (Priority: P5)

7个步骤（RSS拉取→三路抓取→字段择优→AI摘要→向量聚类→聚类扩展→Gravity评分）被编排为一条自动化流水线，每小时触发一次完整周期。每个步骤可独立失败而不影响整体流水线运行。系统24小时无人值守运行，所有步骤的执行状态、成功/失败计数、耗时可被监控。

**Why this priority**: 编排层将各独立功能串联为可靠的端到端系统，是生产级运行的前提。

**Independent Test**: 模拟一个完整周期，人为让其中一个步骤失败（如关闭Firecrawl），验证整条流水线继续运行、失败步骤被记录、最终输出仅缺失该步骤的部分数据。

**Acceptance Scenarios**:

1. **Given** 流水线正常运行, **When** 一个完整周期执行, **Then** 新文章依次经过全部7个步骤并产出最终评分排序结果
2. **Given** 流水线中某一步骤失败, **When** 该文章进入下一步骤, **Then** 系统跳过失败步骤、记录错误日志、继续处理后续步骤
3. **Given** 系统运行24小时, **When** 无人工干预, **Then** 系统至少完成24个完整采集周期且无崩溃
4. **Given** 管理员查看系统状态, **When** 访问监控面板, **Then** 可查看每个步骤的成功率、失败率、平均耗时和最近错误详情

---

### Edge Cases

- 某个RSS源长期不更新（>7天无新文章）时，系统如何处理？降低该源的拉取频率并告警。
- 三路抓取全部失败时，文章标记为"抓取失败"并进入人工审查队列。
- AI摘要引擎返回不符合schema的结果时，系统拒绝该结果并重试，3次失败后标记异常。
- 向量化聚类出现超大聚类（>50篇）时，系统应分裂为子聚类以保持信息粒度。
- Gravity Engine对同类文章评分差异过大（同聚类内方差>阈值）时，触发二次评分校准。
- RSS源返回格式异常（非标准RSS/Atom）时，系统尝试容错解析，失败则记录并跳过。
- 聚类扩展搜索返回大量不相关结果时，仅纳入相似度超过阈值的文章，避免污染聚类。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持配置和管理至少63个RSS源，包括添加、删除、启用/禁用操作
- **FR-002**: 系统 MUST 每小时自动从所有启用的RSS源拉取最新文章
- **FR-003**: 系统 MUST 对每篇新文章并行启动三路内容抓取（Firecrawl、iFramely、Gemini）
- **FR-004**: 系统 MUST 按字段级别独立选择最优抓取结果（标题/正文/图片各自择优）
- **FR-005**: 系统 MUST 对采集的文章进行URL级别去重
- **FR-006**: 系统 MUST 通过AI摘要引擎为每篇文章生成：人类版TLDR、向量版TLDR、5个Key Points、重写标题、分类标签
- **FR-007**: 系统 MUST 将向量版TLDR转换为语义向量并存储
- **FR-008**: 系统 MUST 使用近似最近邻搜索算法自动将语义相似的文章聚类
- **FR-009**: 系统 MUST 在聚类达到3篇文章时触发扩展搜索，主动寻找更多相关报道
- **FR-010**: 系统 MUST 通过Gravity Engine从16个维度对每篇文章进行评分
- **FR-011**: 系统 MUST 基于Gravity Engine输出的Editorial Vote进行最终排序
- **FR-012**: 系统 MUST 过滤掉未通过Novelty Gate的文章，不展示给用户
- **FR-013**: 系统 MUST 在任何单步骤失败时继续处理其余步骤，不中断流水线
- **FR-014**: 系统 MUST 记录每个步骤的执行日志，包括成功/失败状态、耗时、错误详情
- **FR-015**: 系统 MUST 为失败的处理任务提供自动重试机制（最多3次）
- **FR-016**: 系统 MUST 支持24小时无人值守连续运行

### Key Entities

- **Article（文章）**: 系统的核心数据实体。包含原始RSS元数据（标题、链接、发布时间、来源）、三路抓取的原始结果、合并后的最终内容（标题、正文、图片）、处理状态
- **Summary（摘要包）**: 与文章一对一关联。包含人类版TLDR、向量版TLDR、5个Key Points、重写标题、分类标签列表
- **Vector（语义向量）**: 与文章一对一关联。由向量版TLDR生成的高维数学向量，用于相似度计算
- **Cluster（聚类/事件组）**: 一组语义相似文章的集合，代表同一新闻事件。包含聚类ID、包含的文章列表、聚类创建时间、是否触发过扩展搜索
- **GravityScore（编辑评分）**: 与文章一对一关联。包含16个维度的数值评分、Editorial Vote、Novelty Gate判定（pass/fail）
- **RSSSource（RSS源）**: 系统数据源配置。包含源URL、名称、分类、启用状态、最后成功拉取时间、拉取频率
- **PipelineRun（流水线执行记录）**: 每次完整周期的执行快照。包含触发时间、各步骤状态、处理文章数、耗时统计

### Assumptions

- 用户描述中提到的63个RSS源数量是当前规模，系统应设计为可弹性扩展
- "三路抓取"中的字段择优规则（标题用iFramely、正文用Gemini、图片用RSS）是默认策略，系统应支持配置化调整
- Gravity Engine的16维度评分权重可能需要随时间调整，系统应支持权重配置
- 聚类扩展搜索使用外部搜索API，具体提供商由实现阶段决定
- AI模型选择（mini用于摘要、Sonnet用于评分、专用Embedding模型用于向量化）是基于成本-性能权衡的合理默认

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 系统每小时完成一次全量RSS源拉取，成功率≥95%（即≥60/63个源成功拉取）
- **SC-002**: 从文章发现到完成全部7步处理的端到端延迟≤5分钟（单篇文章）
- **SC-003**: 三路抓取容错生效率100%——任一抓取工具不可用时，其余工具自动兜底，文章不丢失
- **SC-004**: AI摘要生成成功率≥98%，且输出严格符合预定义schema
- **SC-005**: 向量聚类准确率≥85%——同一事件的文章被正确归入同一聚类
- **SC-006**: 系统连续运行7天无需人工干预，且无崩溃或数据丢失
- **SC-007**: 通过Novelty Gate的文章中，用户认为"有价值"的比例≥80%（通过抽样评估）
- **SC-008**: 每个流水线步骤的失败不会导致其他步骤中断，容错隔离率100%
